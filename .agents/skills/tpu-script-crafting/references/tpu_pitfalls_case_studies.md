# Case Studies: Ретроспектива ошибок TPU в BEBLaDII

Данный документ обобщает опыт отладки и эволюции скриптов обучения на Google Cloud TPU v6e и Kaggle TPU v5e/v3-8 по итогам анализа 246 коммитов в трех поколениях скриптов:
1. `experiments/Plan A/phase 2/train_phase1_TPU_fsdp.py` (Ранний SPMD/FSDP на TPU v6e-4)
2. `experiments/phase 4/tpu kaggle/train_phase4_tpu_notebook.py` (Диффузия Hierarchical Noise на Kaggle TPU v5e-8)
3. `experiments/phase 6/tpu kaggle/train_phase6_tpu_notebook.py` (Cross-Attention & Conditioning на Kaggle TPU v5e-8)

---

## 1. Шторм перекомпиляций XLA (UncachedCompile Storms)

### Проблема
В PyTorch/XLA граф компилируется статически в байткод XLA HLO при первом запуске. Любое изменение метаданных операций (типы, форма тензоров, значения Python float, используемые напрямую как константы) приводит к инвалидации кеша (`UncachedCompile`) и повторной компиляции графа (1–4 минуты на шаг).

### Исторические примеры
- **Float в Learning Rate (коммиты `f8825ec`, `6d83397`, ADR 079):**
  Шедулер `CosineAnnealingWarmRestarts` на каждом шаге присваивал новое значение `param_group['lr'] = new_lr_float`. XLA вшивал число с плавающей точкой прямо в тело скомпилированного графа. Обучение зависало на 3–5 минут на каждом шаге.
  *Решение:* Переход на постоянный LR (режим PACE с `warmup_steps=0`) либо дискретное обновление LR раз в 50 шагов (`if step % 50 == 1:`), либо тензорное расписание.
- **Pullback Alpha в PACE (коммит `eec0676`, ADR 081):**
  Попытка плавного изменения `pullback_alpha` через `param.data.sub_(param.data - ema, alpha=float_alpha)` вызывала постоянную перекомпиляцию.
  *Решение:* Инициализация `pullback_alpha_tensor = torch.tensor(alpha, dtype=torch.float32, device=dev)` с последующей чисто тензорной арифметикой.
- **Ветвление Python по `torch.rand(1).item() < 0.5` (коммит `ed2df7a` vs ADR 079):**
  Для Self-Conditioning (50% времени подавать нули, 50% — предсказание) в коде стояло `if torch.rand(1).item() < 0.5:`. XLA генерировал два гигантских графа (`TensorsGraphSize ~ 33804`) и постоянно переключался между ними, вызывая бесконечный thrashing.
  *Решение:* Детерминированное in-graph исполнение: прямой проход делается для всего батча, а маска `sc_mask` жестко зануляет ровно первую половину (`batch[:B//2]`).

## 2. Разрыв конвейера TPU: `aten::_local_scalar_dense` и вызовы `.item()`

### Проблема
Вызов `.item()` принудительно синхронизирует CPU хоста с чипом TPU. Все асинхронные очереди операций останавливаются, и хост ждет завершения всех вычислений на TPU.

### Исторические примеры
- **Множественные `.item()` в цикле логирования (коммиты `1ef8359`, `ee3c769`, `95e9411`):**
  В логах WandB вычислялись 28 различных метрик по слоям. Цикл с 28 вызовами `.item()` превращал шаг логирования в 40-секундную паузу.
  *Решение:* Все скалярные тензоры упаковываются в один вектор `torch.stack([...])`, который переносится на CPU за одно обращение: `.cpu().tolist()`.
- **Ловушка с поиском NaN (коммиты `83e1cd4` -> `5d6191f` -> `d28d4c4`):**
  Для отладки NaN был внедрен вызов `check_tensor_nan()` для каждого промежуточного тензора. Внутри стояло `torch.isnan(tensor).any().item()`. Это разорвало граф на десятки изолированных подграфов и мгновенно привело к падению с `RESOURCE_EXHAUSTED` (OOM).
  *Решение:* Все проверки `isnan().any()` собираются в список `GLOBAL_NAN_CHECKS`, объединяются через `torch.stack()`, и их проверка откладывается до конца шага в `torch_xla.sync()`.

## 3. Катастрофический подпороговый коллапс в BF16 (ADR 057, ADR 082)

### Проблема
Установка переменной окружения `os.environ["XLA_USE_BF16"] = "1"` форсирует компилятор XLA понижать точность абсолютно всех операций и весов модели до `bfloat16`. 

### Почему это убило обучение на 15 000 шагов
Мантисса `bfloat16` имеет длину 7 бит (машинный эпсилон $\epsilon \approx 7.8 \times 10^{-3}$).
При шаге оптимизатора AdamW:
$$\Delta \theta = \eta \cdot \frac{m_t}{\sqrt{v_t} + \epsilon} \sim 10^{-6}$$
Относительное изменение веса:
$$\frac{\Delta \theta}{\theta} \approx 10^{-5}$$
Оно оказалось на 2 порядка ниже порога различимости `bfloat16`. Аппаратура TPU буквально зануляла поправки ($\theta + \Delta \theta = \theta$). Веса застыли на месте, а лосс не менялся 15 000 шагов подряд!

### Решение
- Категорически удалить `XLA_USE_BF16 = 1`.
- Обучаемые модули (ModernBERT, AdaLN, проекторы) и буферы оптимизатора строго хранятся в `torch.float32`.
- Только замороженные тяжелые модели (Qwen, VAE Decoder) явно переводятся в `torch.bfloat16` через `.to(torch.bfloat16)`.

## 4. OOM и несовместимость Gradient Checkpointing

### Проблема
На архитектуре ModernBERT (с чередующимися окнами внимания Sliding Window) включение `gradient_checkpointing_enable()` в связке с XLA приводит либо к `AttributeError` (попытка вызвать `getattr(torch, "xla")`), либо к взрыву потребления HBM до 97 ГБ из-за особенностей генерации графа рекомпутации.

### Эволюция проблемы (коммиты `dc7cfd4`, `d2e37d2`, `850ed62`, `3e73b8b`)
1. Сначала пытались манки-патчить: `DummyXLA` и `preserve_rng_state=False`.
2. Граф вырос до 93GB на TPU v6e при батче 4. Пришлось уменьшать батч до 1.
3. В конечном итоге в [ADR 005](../../.know/decisions/005_modernbert_xla_gradient_checkpointing.md) было зафиксировано решение: **полностью отключить Gradient Checkpointing на XLA для ModernBERT** и вместо этого шардировать веса через SPMD/FSDP.

## 5. Ошибки сохранения/загрузки чекпоинтов и EMA Shadows

### Повреждение теней EMA при Resume (ADR 080)
- **Ошибка:** При возобновлении обучения словарь теней обновлялся как `ema.shadow.update(ema_update)`. В результате шардированные тензоры на `xla:0` были заменены обычными тензорами на CPU! При следующем шаге `ema.step()` происходил сбой топологии.
- **Решение:** In-place копирование строго в целевой девайс:
  ```python
  if target_key in ema.shadow:
      ema.shadow[target_key].copy_(v.to(device=ema.shadow[target_key].device, dtype=torch.float32))
  ```

### Оценка LIVE весов вместо EMA
- Валидация запускалась как `model.eval()`, из-за чего замерялись «сырые» шумные веса оптимизатора.
- **Решение:**
  ```python
  model.eval()
  ema.apply(actual_model)
  try:
      # Валидационный цикл...
  finally:
      ema.restore(actual_model)
      model.train()
  ```

### Ошибки FSDP при загрузке весов (ADR 006, коммит `1634e88`)
- Попытка загрузить веса в модель ПОСЛЕ её обертки в `SpmdFullyShardedDataParallel` разрушает внутренние дескрипторы шардирования (`xs.mark_sharding`) и вызывает мгновенный OOM.
- **Решение:** Веса модели загружаются строго ДО обертки FSDP! Оптимизатор и планировщик загружаются ПОСЛЕ FSDP.
