# Идея: Tool Calling через Латентный Inpainting и RAG-Similarity

> Автор: AI Agent (со слов автора архитектуры) | Дата: 2026-05-15
> Статус: Концепт. Реализуется в Phase 4+ (после обучения декодера).

---

## Ключевая идея

Вместо классического подхода "fine-tuning на [TOOL_CALL] токенах" — инструменты реализуются как
**отдельная RAG-база** ("RAG контекста задачи"), а вызов инициируется не моделью напрямую,
а **Оркестратором** по сигналу релевантности. Заполнение параметров — через
**denoising зашумлённого JSON-шаблона** (латентный inpainting).

Это устраняет три главных провала LLM в tool calling:
- галлюцинацию имён полей (структура зафиксирована в шаблоне),
- забывание инструментов (они в RAG, не в весах),
- невозможность добавить новый инструмент без дообучения (просто добавить в RAG).

---

## Архитектура: три компонента

### 1. RAG Контекста Задачи (Tool Registry)

Отдельная векторная база от основной RAG-базы знаний. Содержит:
- Описания доступных инструментов (что делает, когда применять).
- Точные данные: имена файлов, сигнатуры функций, JSON-схемы параметров, примеры вызовов.
- Шаблоны JSON для каждого инструмента (структура без значений).

**Ключевой принцип:** здесь хранится то, что лучше скопировать точно,
чем "вспоминать" из весов модели. Имена функций, пути, форматы — в RAG, не в модели.

### 2. Оркестратор: Детекция намерения вызова инструмента

При каждом шаге рассуждения Оркестратор выполняет similarity search **одновременно**
в двух базах:
- Основной RAG-базе знаний (факты, контекст задачи).
- RAG контекста задачи (Tool Registry).

Если топ-1 результат поиска — чанк из Tool Registry с релевантностью выше порога θ:
→ Оркестратор **прерывает** основную диффузию и инициирует Tool Call subprocess.

Порог θ — гиперпараметр Оркестратора (не модели). Настраивается без дообучения.

### 3. Tool Call Subprocess: Латентный Inpainting

Когда Оркестратор детектирует намерение вызова инструмента:

```
┌─────────────────────────────────────────────────────────┐
│  ОСНОВНАЯ ДИФФУЗИЯ (шаг t, уровень шума σ_t)           │
│  Текущее латентное состояние z_t → СОХРАНИТЬ           │
└───────────────────────┬─────────────────────────────────┘
                        │ ПАУЗА
                        ▼
┌─────────────────────────────────────────────────────────┐
│  TOOL CALL SUBPROCESS                                   │
│                                                         │
│  RAG вход:    текущий прогресс рассуждения (z_t)        │
│  Prompt:      "Заполни параметры для вызова [Tool X]"   │
│               (вместо исходного промпта задачи)         │
│  Рабочее     JSON-шаблон с зашумлёнными параметрами     │
│  пространство: {"func": "X", "arg1": [ШУМ], ...}       │
│                                                         │
│  Модель:      Denoise только значения параметров.       │
│               Структура JSON физически не может         │
│               быть сломана — она фиксирована.           │
│                                                         │
│  Декодер:     Восстановить конкретные значения из z     │
│  Оркестратор: Запустить инструмент с этими параметрами  │
│  Результат:   Добавить в RAG контекста как новый чанк   │
└───────────────────────┬─────────────────────────────────┘
                        │ ВОЗОБНОВЛЕНИЕ
                        ▼
┌─────────────────────────────────────────────────────────┐
│  ОСНОВНАЯ ДИФФУЗИЯ (возобновление)                      │
│  Контекст обогащён результатом инструмента.             │
│  Noise schedule: рассмотреть откат на Δt шагов назад    │
│  чтобы дать модели время "переосмыслить" с новым        │
│  знанием перед финальными шагами деноизинга.            │
└─────────────────────────────────────────────────────────┘
```

---

## Почему это работает лучше классического подхода

| Свойство | Классический fine-tuning | Latent Inpainting |
|---|---|---|
| Структура JSON | Генерируется полностью, риск галлюцинаций | Фиксирована шаблоном, невозможно сломать |
| Добавление нового инструмента | Дообучение модели | Добавить чанк в RAG |
| Выбор инструмента | Встроен в веса (дорого) | Similarity search (бесплатно) |
| Точность имён полей | Зависит от fine-tuning данных | Всегда 100% (шаблон) |
| Расширяемость | Ограничена контекстным окном | Ограничена размером RAG |

---

## Аналогия с Image Diffusion

Это прямой аналог **inpainting** в image diffusion (DALL-E, Stable Diffusion):
- Там: фиксируется часть изображения (маска), зашумляется другая часть, модель восстанавливает.
- Здесь: фиксируется структура JSON (ключи), зашумляются значения параметров, модель восстанавливает.

Inpainting в image diffusion — давно решённая задача. Перенос на структурированный текст
является естественным расширением того же принципа.

## Открытые вопросы

### 1. Noise schedule при возобновлении
Когда основная диффузия паузится на шаге `t` (уровень шума `σ_t`), а потом возобновляется
с новым контекстом (результатом инструмента):
- **Вариант A:** Продолжать с того же `σ_t` — быстро, но модель может не успеть "обдумать"
  новую информацию.
- **Вариант B:** Откатиться на Δt шагов назад (добавить чуть шума) — медленнее, но
  семантически корректнее. Аналог guided diffusion с новым условием.
- Требует экспериментального подбора. Предположительно Δt ≈ 10-20% оставшихся шагов.

### 2. Обучающие данные для inpainting параметров
Нужны примеры "зашумлённый JSON-шаблон → заполненные параметры".
Источники:
- ToolBench, APIBench, Berkeley Function-Calling Leaderboard датасеты.
- Синтетическая генерация: взять любой датасет с function calls, создать шаблоны
  автоматически из JSON-схем.
Значительно проще, чем обучать полную JSON-генерацию с нуля.

### 3. Порог θ для детекции инструмента
Слишком низкий → ложные вызовы инструментов посреди рассуждения.
Слишком высокий → инструменты не вызываются когда нужны.
Возможное решение: adaptive threshold, калибруемый на held-out задачах с известными ответами.

## Требования к реализации

- **Phase 4:** Обучение декодера (text generation из латентного пространства).
  Для tool calling декодер должен уметь восстанавливать конкретные примитивные значения
  (строки, числа, булевы) из латентного z. Это существенно проще, чем полная генерация текста.
- **Оркестратор:** Dual-RAG search + порог θ + управление noise schedule при возобновлении.
  Реализуется на уровне inference pipeline, не модели.
- **Tool Registry:** Формат чанков для описания инструментов. Стандартизировать структуру
  (описание + схема + шаблон JSON) чтобы similarity search находил правильный инструмент.
