## Главные гипотезы (по приоритету)

### 🔴 КРИТИЧЕСКОЕ: EMA pullback уничтожает обновления

**Это наиболее вероятная основная причина.**

PACE pullback работает как: после каждого шага оптимизатора:
```
param ← param - pullback_alpha * (param - ema_shadow)
```

При очень маленьком LR (`dus_lr = 1e-6`) шаг оптимизатора вносит обновление порядка **~1e-7 – 1e-8** (LR × grad). А pullback с `alpha=0.001` тянет параметр обратно к EMA с силой **~1e-3 × отклонение_от_EMA**.

Это создаёт **дисбаланс**: pullback на **3–5 порядков сильнее** шага обучения. Получается, что при каждом шаге:
1. Оптимизатор вносит микроскопическое обновление Δ
2. Pullback **почти полностью отменяет** это обновление, затягивая параметр обратно

При этом EMA тоже практически не движется (decay=0.99, shadow ≈ параметрам). Система входит в **паразитное равновесие**: loss не падает, но и не взрывается.

**Контрдовод (но не опровержение):** на GPU тот же PACE работает → значит на GPU LR достаточно высок, чтобы выйти за пределы pullback-зоны. На TPU `dus_lr = 1e-6` (Попытка 2) — это в 20 раз меньше GPU LR.

> **Доказательство из графиков**: `pullback_alpha` резко падает с 0.02→0.002 в первые ~400 шагов (warmup завершается), после чего loss **не меняется**. Даже после снижения pullback улучшений нет — это указывает, что проблема не только в pullback, но и в самом LR.

---

### 🔴 КРИТИЧЕСКОЕ: LR слишком мал для TPU-батча

Вы масштабировали LR down с GPU:
- GPU: `batch=?`, `dus_lr=2e-5`
- TPU: `batch=64`, `dus_lr=1e-6` (Попытка 2) — снижение в **20 раз**

Но на TPU с SPMD батч размазан по 8 ядрам. Эффективный `batch_per_device = 64 / 8 = 8`. Это **меньше** GPU батча, а не больше. Если вы масштабировали LR под `batch=64` считая его единым — вы ошиблись вдвойне:
- Реальный эффективный батч на устройство — маленький
- LR снижен слишком сильно

**Формула линейного скейлинга LR**: если GPU работал с `batch=B_gpu` и `lr=2e-5`, то для `effective_batch=64` на TPU нужно `lr = 2e-5 × (64 / B_gpu)`. Если `B_gpu > 64` — LR должен быть **меньше**, но если `B_gpu=8` — LR должен быть в 8 раз **больше**.

### 🟡 ВАЖНОЕ: EMA инициализирована из сырых весов Phase 3, не из GPU-чекпоинта

Посмотрите на `val_sc_w_norm`:
- Попытка 2: **две горизонтальные линии** (~31 и ~0) — это значит, что `self_cond_proj` в EMA и в текущей модели **не обновляются синхронно**.
- `sc_w_norm ≈ 31` практически не меняется — это норма Xavier-инициализированного слоя 1024×1024, который стоит на месте.

При resume из GCS: если `self_cond_proj` не было в старом чекпоинте, он заново инициализируется с xavier (строки 1357–1365). Но **EMA shadow для него инициализируется из параметров модели в момент создания EMA** (до загрузки чекпоинта). Порядок операций в `train()`:

```python
ema = EMA(actual_model, ...)       # ← EMA создаётся из НУЛЕВОГО sc_proj
...
start_step, ... = load_checkpoint_split(...)   # ← sc_proj re-init xavier
# Потом: ema.shadow['self_cond_proj.weight'] содержит НУЛИ, а параметр xavier!
```

Это означает: при каждом `ema.step()` pullback тянет `self_cond_proj` к **нулевым теням EMA**, нейтрализуя обучение SC.

> ⚠️ **Конкретная ошибка в коде**: EMA создаётся до `load_checkpoint_split`. После загрузки чекпоинта параметры модели меняются (в т.ч. re-init sc_proj), но EMA shadow остаётся построенным из **до-загрузочных весов**.

### 🟡 ВАЖНОЕ: Validation на EMA-весах vs обучение на raw-весах — несоответствие

```python
if step > start_step and (step + 5) % args.val_steps == 0:
    ema.apply(actual_model)   # ← EMA weights
    ...
    ema.restore(actual_model)
```

Условие `(step + 5) % 200 == 0` означает, что validation срабатывает на шагах: 195, 395, 595... (т.е. смещённых на -5). Это незначительная проблема, но создаёт путаницу при анализе.

---

### 🟡 ВАЖНОЕ: PACE pullback_warmup_on_resume=True — повторный warmup

На каждой новой Kaggle-сессии `pullback_warmup_on_resume=True` запускает pullback от `0.03 → 0.001` заново. Это видно на обоих графиках `pullback_alpha` — резкое падение в начале.

Проблема: при `pullback_warmup_start=0.03` модель первые 200 шагов получает **очень агрессивный pullback** (в 30 раз сильнее base). Это означает, что самое начало каждой сессии — сильный откат к EMA, что с каждой сессией "замораживает" модель всё сильнее.

---

### 🟠 ВЕРОЯТНОЕ: XLA_USE_BF16=1 — принудительный bfloat16

`os.environ["XLA_USE_BF16"] = "1"` конвертирует **все** тензоры в bfloat16, включая float32 параметры DUS (которые должны быть float32 согласно ADR 057).

В GPU-версии этого флага нет. На TPU:
- Градиенты вычисляются в bfloat16 → потеря точности
- Обновления весов мелкие (LR=1e-6) → при bfloat16 округление **уничтожает** микро-обновления
- Минимальный ненулевой шаг bfloat16 ≈ 2^-7 × значение ≈ 0.0078 для веса ~1.0

При `lr=1e-6` и `grad~0.1`: шаг = `1e-7`. В bfloat16 с весом `w~1.0` это **субэпсилонное обновление — оно округляется в ноль**.

> **Это может быть самой главной причиной**: на GPU работает float32, на TPU XLA_USE_BF16 переводит всё в bfloat16, и микроскопические градиентные обновления просто **пропадают при округлении**.

## Итоговая таблица причин

| # | Причина | Тяжесть | Уверенность |
|---|---|---|---|
| 1 | `XLA_USE_BF16=1` уничтожает суб-epsilon обновления при LR=1e-6 | 🔴 Критическая | 85% |
| 2 | LR слишком мал — неправильное масштабирование под SPMD | 🔴 Критическая | 80% |
| 3 | EMA shadow инициализируется до загрузки чекпоинта | 🟡 Важная | 70% |
| 4 | PACE pullback агрессивнее LR шага на 3+ порядка | 🔴 Критическая | 75% |
| 5 | `pullback_warmup_on_resume` "замораживает" модель при каждой сессии | 🟡 Важная | 60% |

## Рекомендуемые исправления

### Fix 1 — Убрать или ограничить XLA_USE_BF16

```python
# БЫЛО:
os.environ["XLA_USE_BF16"] = "1"

# СТАЛО: убрать совсем или использовать явное приведение только для forward
# Параметры DUS должны оставаться float32 для корректного обновления при малом LR
```

Альтернатива: оставить bfloat16 для forward, но сохранить **master copy** весов в float32 (как это делает `apex.amp`). Для XLA это достигается через `XLA_DOWNCAST_BF16` вместо `XLA_USE_BF16`.

### Fix 2 — Поднять LR

Если GPU работал с `dus_lr=2e-5`, то для TPU (`effective_batch ≈ 8`):
- Linear scaling: `lr_tpu = 2e-5 × (8 / B_gpu)`
- Если `B_gpu = 8`: `lr_tpu = 2e-5` (тот же LR!)
- Если хотите 64 как "суммарный": `lr_tpu = 2e-5 × (64/8) / (64/8) = 2e-5`

**Рекомендуемые значения для следующего запуска**:
```python
dus_learning_rate = 5e-5   # Вернуться к диапазону GPU
new_layers_lr     = 5e-4
```

### Fix 3 — Порядок создания EMA

```python
# БЫЛО:
ema = EMA(actual_model, ...)           # EMA из исходных весов
start_step, ... = load_checkpoint_split(...)  # Меняет веса!

# СТАЛО:
start_step, ... = load_checkpoint_split(...)  # Сначала загружаем
ema = EMA(actual_model, ...)           # EMA из ПРАВИЛЬНЫХ весов
# (EMA shadow из чекпоинта загружается отдельным кодом после)
```

> **Важно**: при таком порядке нужно сохранить логику загрузки EMA shadow из чекпоинта.

### Fix 4 — Снизить или убрать PACE при малом LR

Если `LR = 1e-6`, то pullback_alpha должен быть **на 2+ порядка меньше LR**:
```python
pullback_alpha = 1e-4  # Вместо 0.001
pullback_max   = 3e-4  # Вместо 0.003
```

Или временно отключить PACE совсем (`optimizer_mode = "cyclic"`) и проверить, движется ли loss.

### Fix 5 — Отключить warmup при resume

```python
pullback_warmup_on_resume = False
```

Это позволит не сбрасывать pullback к агрессивному `0.03` при каждой новой сессии.

## Диагностический тест

Чтобы подтвердить гипотезу №1 (bfloat16):

```python
# Добавить в начало обучения (первые 10 шагов):
for name, param in actual_model.named_parameters():
    if param.requires_grad:
        print(f"{name}: dtype={param.dtype}, data_abs_mean={param.data.abs().mean()}")
```

Если dtype = `bfloat16` при ожидаемом `float32` — это прямое подтверждение.

Также можно добавить логирование нормы **фактического обновления** весов:
```python
# После optimizer.step(), перед ema.step():
with torch.no_grad():
    for pg in optimizer.param_groups:
        for p in pg['params'][:3]:
            if p.grad is not None:
                update_size = (p.grad * pg['lr']).norm().item()
                print(f"Update size: {update_size:.2e}, dtype={p.dtype}")
```
