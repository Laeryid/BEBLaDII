# Идеи радикального сжатия всех компонент BEBLaDII Plan C

Сводный план сжатия всей системы (Энкодер + Декодер + Диффузионное ядро) — от быстрых приёмов без переобучения до пересборки «Plan C v2» с компактной Системой 1 и **контекстным обучением MLM / Masked Cell Prediction (MCP)** в Phase 1 для формирования композиционной семантики (`аренда = дом ⊕ платёж`) без дистилляции чужих моделей.

---

## 0. Сводка: «Сейчас → Сжатый Plan C v2»

| Компонента | База Plan C (сейчас) | Умеренный v2 (`d_emb=384`, `standard`) | Радикальный v2 (`d_emb=256` + MLM/MCP, `tiny`) | Главный рычаг сжатия |
|---|---:|---:|---:|---|
| **Энкодер (`embeddings` + слои)** | **161.4M** (616 MB FP32) | **~54M** (206 MB / **103 MB BF16**) | **~37M** (141 MB / **71 MB BF16**) | `d_emb: 1024 → 256..384` + `ContextSyntax 256d` + `LexicalMLP` |
| **Декодер (без `tied lm_head`)** | **52.9M** (202 MB FP32) | **~6.8M** (26 MB / **13 MB BF16**) | **~3.5M** (13 MB / **7 MB BF16**) | `dec_context → GrassLocal` (23×) + `dec_smooth: 1024 → 256..384` |
| **Диффузионное ядро (Phase 3)** | **167.9M** (640 MB FP32) | **38.6M** (147 MB / **74 MB BF16**) | **27.9M** (106 MB / **53 MB BF16**) | `GrassFull/Local` + `2×GrassCA` + `3-slot DCA` *(уже готово)* |
| **ИТОГО вся система** | **382.2M** (**1.46 GB** FP32 / 730 MB BF16) | **~99.4M** (**379 MB** FP32 / **190 MB BF16**) | **~68.4M** (**260 MB** FP32 / **130 MB BF16**) | **3.8× – 5.6× меньше параметров** *(+ с INT8 на словаре: ~90–120 MB целиком!)* |

*(Дополнительно: при переходе со словаря `131K` на целевой `48K–64K` вся Система 1 сжимается ещё примерно в **2×**.)*

## 1. Энкодер (`GrassmannianEncoder`: `161.4M → 37–54M`)

### 1.1. Сужение таблицы `embeddings` (`131072 × 1024 → 256..384`) + контекстный MLM / MCP в Phase 1
- **Экономия:** `134.2M (512 MB)` → **`33.5M (128 MB)`** при `d_emb=256` (**4×**) или **`50.3M (192 MB)`** при `d_emb=384` (**2.7×**).
- **Диагноз текущих весов (`encoder/weights.pt`):** реальный `eff_rank = 682.2`; `top-256` объясняют **59.8%** дисперсии, `top-384` — **70.3%**, `top-512` — **78.1%**.
- **Ключевой риск при чистом автоэнкодере:** если просто сжать `embeddings` до `256` на чисто реконструктивном лоссе (`ids → Gr → ids`), автоэнкодер вместо композиции смыслов строит плотный «сферический хэш», и проседает реконструкция редких слов.
- **Выбранное решение — Контекстный лосс Phase 1 (MLM + Masked Cell Prediction, без дистилляции учителей):**
  - **Механизм:** на части батчей (или в каждом батче для 15–25% позиций) маскируем отдельные токены (MLM) и/или целые клетки по 4 токена (Masked Cell Prediction) *на входе* Энкодера, требуя от системы восстановить замаскированные токены из окружающего контекста:
    $$\mathcal{L}_{\text{Phase1}} = \mathcal{L}_{\text{rec}}(\text{visible}) + \lambda_{\text{mlm}}\,\mathcal{L}_{\text{rec}}(\text{masked}) + \mathcal{L}_{\text{KL}} + \mathcal{L}_{\text{rank}}$$
  - **Почему это даёт настоящую генерализацию на все `131K` токенов:**
    - в отличие от словарных пар (`аренда ↔ плата за дом`), которые двигают только строки из списка, обычный текст пропускает через контексты **все** слова словаря (включая редкие `"субаренда"`, `"лизинг"`, `"ипотека"`), выстраивая их строки в `embeddings` вдоль общих смысловых направлений;
    - теснота `d_emb = 256..384` лишает модель «ленивого» пути (отдельной ортогональной оси под каждое слово) и подталкивает раскладывать сложные понятия по переиспользуемым осям в $\mathrm{Gr}(8, 128)$ (`аренда ≈ дом ⊕ платёж`);
    - собственная геометрия $\mathrm{Gr}(8, 128)$ формируется чисто, без конфликта с геометрией внешних моделей-учителей.
  - **Практическая деталь:** чтобы MLM-маскирование не ломало точность кодирования *чистых* ячеек, полезно либо держать умеренную долю маскирования (15% токенов, `λ_mlm ≈ 0.3`), либо чередовать чистые батчи (точная реконструкция) и MLM/MCP-батчи (композиционная геометрия), а `ContextSyntaxEncoder` при этом естественным образом учится передавать контекст в синтаксические/семантические оси.

### 1.2. Сужение `ContextSyntaxEncoder` (`1024 → 256`, **14× сжатие**: `21.1M → ~1.5M`)
- Сейчас 2 слоя `ModernBERTLayer(1024, 2048)` работают ради `syntax_proj(1024 → 128)` (`8 × 16` каналов синтаксиса).
- Сжатие `hidden_size = 256, intermediate_size = 512` оставляет **двукратный запас** относительно выхода `128`, срезая **~19.5M** параметров практически без потери качества.

### 1.3. Компактный `LexicalCoreMLP` (`6.0M → ~1.5–2.2M`) + опциональная разреженность
- При `d_emb = 256..384` и `intermediate = 768..1024` проекция `d_emb → 8 × 112` весит в **3–4×** меньше.
- *Идея для усиления композиционности:* добавить мягкую разреженность активаций (`L1` на `gate * up` или `Top-K` в `LexicalCoreMLP`), чтобы каждый токен строился как комбинация **малого числа** (например, 8–16) переиспользуемых смысловых атомов.

### 1.4. Радикальные резервы по словарю (если идти ещё дальше)
1. **Частотно-кластеризованные эмбеддинги (Adaptive Embedding):**
   - `top-16K` частых токенов: полная размерность `512d` (`8.2M`);
   - `16K..64K`: `256d` + линейка `256 → 512` (`12.4M`);
   - `64K..131K` (длинный хвост): `128d` + линейка `128 → 512` (`8.6M`);
   - Итого: **`~29.2M`** вместо `134.2M` (**4.6× сжатие** при полном `512d` качестве на 95% реального текста!).
2. **Компактный целевой токенизатор (`48K–64K` вместо `131K`):**
   - если целевые языки ограничены (RU + EN + Code), уменьшение словаря в **2–2.7×** линейно сжимает `embeddings`, `tied lm_head` и ускоряет `NoiseRadarHead` + `CE`-лосс в те же **2–2.7×**.

## 2. Декодер (`GrassmannianDecoder`: `52.9M → 3.5–6.8M`, **7.5× – 15× сжатие**)

### 2.1. Замена `dec_context_layer` на `GrassLocal` (`10.5M → 0.45M`, **23× сжатие**)
- В `decoder/__init__.py` `dec_context_layer` принимает `(B, N, 8, 128)` до распаковки `1 → 4` и возвращает дельту на `(B, N, 8, 128)`.
- Прямая замена `ModernBERTLayer(1024, 2048)` на `GrassmannianSABlock(local_radius=4..6)` экономит **10M** параметров и геометрически идеально согласуется с `O(8)`-распаковщиком `SetCrossAttentionUnpacker`.

### 2.2. Сужение `dec_smooth_layers` (`4 × ModernBERT(1024)` = `42.0M` → `2.6–5.9M`, **7× – 16× сжатие**)
- **Главное обоснование из кода:** `SetCrossAttentionUnpacker` на выходе уже имеет узкое место **`128 + 128 = 256`** (`h_attn || h_gram`), которое сейчас искусственно раздувается `Linear(256 → 1024)`.
- Снижение ширины 4 сглаживающих слоёв:
  - `hidden = 384, ffn = 768` → **~5.9M** (**7.1×** меньше);
  - `hidden = 256, ffn = 512` → **~2.6M** (**16×** меньше).
- Если `embeddings` остаётся `512` или `1024`, в самом конце перед `tied lm_head` ставится одна проекция `Linear(384, d_emb)` (`~0.2–0.4M`).
- **Побочный ускоритель обучения Phase 3:** при `d_emb = 256..384` вычисление `NoiseRadarHead.compute_dict_stats` и токенного `CE`-лосса (`131072 × d_emb`) ускоряется ровно в **2.7× – 4×** (главное узкое место на CPU!).

### 2.3. Алгоритмическое ускорение `NoiseRadarHead` и `CE`-лосса (`131K × 1024`, без переобучения)

Матрица `lm_head_weight (131072 × 1024)` полностью заморожена — по ней можно один раз построить индекс и ускорить оба узких места, учитывая их разную математику (`NoiseRadar` — чистый `no_grad` Top-2 поиск; `CE` — нужен несмещённый градиент знаменателя softmax):

- **Для `NoiseRadarHead.compute_dict_stats` (`no_grad`, Top-2 косинус):**
  1. **Сферический IVF (K-Means Coarse-to-Fine):** кластеризуем нормированный словарь на $K{=}512..1024$ центроидов; ищем `nprobe=4..8` кластеров (~1000–2000 кандидатов) и считаем точный `1024d` косинус → **40–80× быстрее**, точность `>99%`.
  2. **SVD-отбор (`r=128`) + Exact Re-rank (и Exact MIPS Pruning по Коши–Шварцу):** грубый отбор `top-128` в `128d` (опционально `INT8`) + точный `1024d` реранк → **10–25× быстрее**, точность `99.5–100%`.
  3. **Ready-made ANN для CPU (`FAISS IVFPQ + refine` / `usearch` / `hnswlib`):** `2000` запросов за ~10–30 мс (**50–150×** на CPU).
  4. **Бесплатные фиксы:** убрать принудительный `FP32`-каст весов в `compute_dict_stats` (считать `h_unit @ U_bf16.T` в `BF16/FP16` или per-row `INT8` — сразу **2–8×** быстрее); на CPU — 2-ступенчатый частотный фильтр (`top-16K` с ранним выходом при `cos_max > 0.45`).
- **Для `compute_decoder_ce_loss` (градиент по словарю `131K × 1024`):**
  1. **Stratified Sampled Softmax + Hard Negatives:** для активных токенов считаем логиты по малому пулу `tgt + hard negatives + случайный хвост` с importance-поправкой `+ln(|V_tail|/N_rand)`. **Математический нюанс:** несмещённой является оценка суммы хвоста $\hat{Z}_{\text{tail}}$, а сам `CE` как $\log \hat{Z}$ систематически занижен по неравенству Йенсена (и градиент смещён тем сильнее, чем ниже recall реальных жёстких негативов — см. фактические замеры ниже!).
  2. **Batch-Shared Pool (`K_pool = 4096..8192`):** единый статический пул на весь батч → один плотный GEMM `(M, 1024) @ (1024, K_pool)` со 100% статическими формами для XLA. **Ограничение:** при `M = 512` разных токенов общий пул `K_hard = 1536` выделяет в среднем всего 3 слота на токен, чего не хватает для острых распределений (`t ≤ 0.25`).
  3. **Cut Cross-Entropy (Apple, 2024 / Liger Kernel) / точный Chunked Online Softmax:** **100% точный** градиент и `0 MB` на полные логиты (`2–4×` быстрее наивного FP32 CE на GPU). По итогам проверки точности именно точный chunked/CCE предпочтительнее для боевого обучения на GPU/TPU при `ce_weight > 0`.
  4. **Случайная статическая фильтрация батча до `decoder.decode_hidden`:** прогонять через 4 слоя `ModernBERT(1024)` фиксированные `B_ce = ceil(B * fraction)` примеров **случайно среди имеющих хотя бы один активный токен** (`ce_batch_select="random"`, дефолт в `vocab_optim.py`). **Важно:** вариант `max_active` (выбирать примеры с максимумом активных токенов) вносит систематическое смещение — короткие ответы почти никогда не получают CE-градиент.

#### Фактическая проверка точности на реальном словаре (`exp_vocab_fidelity.py`)

Синтетические тесты на низкоранговой/случайной матрице (`CE ≈ ln V` или `rank(W) = 32`) давали обманчивые `grad_cos = 0.9997–1.0000`. Проверка на **реальном полноранговом словаре `131,072 × 1024`** и реальных скрытых состояниях замороженного Декодера Системы 1 (`16` примеров, `1947` валидных токенов, `M=512`, `K_hard=1536`, `K_rand=2048`, `svd_rank=64`, `3` повтора хвоста) показала:

1. **`NoiseRadarHead` в `BF16` vs оригинальный `FP32` — чистая победа без потерь:**
   - `t = 0.00`: `cos_gap = 0.0236`, ошибка `cos_gap = 3.81e-4` (**`1.6%`**), `Δσ_tok = 9.7e-6`, согласие argmax **`1.0000`**, `TokAcc 0.974 → 0.974`, `CE 0.115 → 0.115`.
   - `t = 0.25`: `cos_gap = 0.0189`, ошибка `cos_gap = 3.76e-4` (**`2.0%`**), `Δσ_tok = 4.1e-5`, согласие argmax **`1.0000`**, `TokAcc 0.946 → 0.946`, `CE 0.259 → 0.259`.
   - `t = 0.50`: `cos_gap = 0.0129`, ошибка `cos_gap = 4.18e-4` (**`3.3%`**), `Δσ_tok = 8.3e-5`, согласие argmax **`1.0000`**, `TokAcc 0.530 → 0.530`, `CE 2.538 → 2.538`.
2. **`Batch-Shared Sampled CE` (`SVD rank=64`, `K_hard=1536`, `K_rand=2048`) — критерий приёмки (`grad_cos ≥ 0.98`, `|bias| ≤ 2%`) НЕ пройден:**
   - `t = 0.00` (`CE_exact = 0.1147`): `bias = -34.0%` (FP32) / **`-40.3%`** (BF16), `grad_cos = 0.717 / 0.691`, `Recall@10 = 0.204 / 0.212`, инфляция `TokAcc: 0.974 → 0.992`.
   - `t = 0.25` (пик веса `w_t` в обучении, `CE_exact = 0.2586`): `bias = -30.2%` / **`-32.5%`**, `grad_cos = 0.763 / 0.758`, `Recall@10 = 0.263 / 0.278`, инфляция `TokAcc: 0.946 → 0.977`.
   - `t = 0.50` (`CE_exact = 2.5377`): `bias = -10.7%` / `-10.9%`, `grad_cos = 0.912 / 0.916`, `Recall@10 = 0.467 / 0.480`, инфляция `TokAcc: 0.530 → 0.607`.
   - **Вывод и реализованное решение:** причина провала — полноранговый спектр реальной `lm_head` (`rank=64` слишком груб) и нехватка слотов общего пула (`1536 / 512 = 3` слота на токен при острых распределениях). В `vocab_optim.py` и `train_phase3_alt.py` теперь **по умолчанию включён 1-проходный `Online Chunked Exact CE`** (`--ce-mode exact_chunked`, `chunk=16384`): сохраняются `NoiseRadar BF16` и случайная фильтрация `B_ce` до `decode_hidden`, а сам `lm_head` CE считается **точно** по всему словарю (`0.00%` смещения, `grad_cos = 1.000000`, точный `TokAcc`, пик памяти `~32 MB` вместо `>530 MB`, 2 GEMM за fwd+bwd без повторного пересчёта). Режим `--ce-mode sampled` оставлен опционально; метрику `train/ce_tok_acc` из sampled-пула нельзя сравнивать с точным `val/tok_acc` из-за завышения на `+2..+8 п.п.`.

## 3. Диффузионное ядро (`GrassmannianAltDiffusionCore`: `167.9M → 27.9–38.6M`, резерв до `~15M`)

Уже реализовано в `train_phase3_alt.py` (**4.35× – 6.0×** сжатие против 167.9M):
- `GrassFull` / `GrassLocal` (`0.45M/слой`), 2× `GrassCA` (`0.51M/слой`), `GrassPromptAdapter` (`0.50M`), 3-слотовый `PerAxisGRNv3` DCA (`<0.01M` суммарно), 3× `FullSABlock` (`33.1M` в `standard` / `23.7M` в `tiny`).

### Куда можно сжать ещё глубже (и одновременно улучшить качество):
1. **Обучаемый эмбеддинг ранга оси `axis_emb[0..7]` (`8 × 128` на слой, +10K параметров на всю сеть):**
   - закрывает «слепоту» поосевого `GrassSA`/`GrassCA` к иерархии осей ($k=0$ против $k=7$) при высоком шуме $t \to 1$, когда нормы всех 8 осей выравнены шумом.
2. **Рекурсивный шаринг весов `FullSABlock` (ALBERT / Universal Transformer стиль):**
   - 86% всех весов `standard` (33.1M из 38.6M) лежат в 3 слоях `FullSABlock`.
   - Если шарить матрицы `q/kv/o/ffn` одного `FullSABlock` между слоями `2, 6, 9`, но оставить **уникальные `AdaLN` + `DCA` (`PerAxisGRNv3`)** на каждой глубине, модель `standard` сожмётся с **38.6M до ~16.5M** (в **10× меньше** базовой 167.9M!), сохранив глубину 10 слоёв и все маршруты DCA.
3. **Low-Rank / Bottleneck FFN в `FullSABlock`:**
   - замена плотных `1024 → 2048 → 1024` на факторизованный `1024 → 512 → 2048 → 512 → 1024` (или расширение только на среднем «смысловом» слое `6`, а слои `2` и `9` сделать `ffn=1024`) режет параметры ещё на **30–40%**.
4. **Геометрическая + data-driven инициализация (`INIT_OPTIMIZATION_IDEAS.md`):**
   - ускоряет сходимость компактных ядер, компенсируя меньший запас параметров.
5. **Геометрически-согласованные формы матриц (подробно в `ARCHITECTURE_AND_IDEAS.md`, раздел 10):**
   - **PHM-проекции** ($W = \sum_{m=1}^r A_m \otimes F_m$, $r=2..4$) в `FullSABlock` — сжимают `1024 × 1024` в **16–32×** по весам и **2–4×** по FLOPs, опуская весь `standard` до **~8–12M** параметров при полном кросс-осевом смешивании;
   - **Грассманиановый скор $\|Q_i K_j^\top\|_F^2$ + Procrustes-роутер $M_{ij}$ без SVD** — точная инвариантность к повороту осей при $N \times N$ (`128 × 128`) softmax вместо `(4, 1024, 1024)`;
   - **Билинейный шаг $L \cdot X \cdot R$** (`L ∈ R^{8×8}`, 64 параметра/слой) в `GrassSA` — дешёвый кросс-осевой обмен, позволяющий сократить число `FullSABlock`.

## 4. Сжатие без переобучения (Zero-Retrain, доступно прямо сейчас)

| Действие | Было | Станет | Потеря качества |
