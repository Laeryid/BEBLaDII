# ADR 078: Корректировка гиперпараметров для TPU (Batch 64) и фикс XLA рекомпиляции

## Дата
2026-09-01

## Контекст (Context)
При переходе с GPU (T4x2, DataParallel, batch size = 8) на TPU v5e-8 (SPMD, batch size = 64) для Phase 4, возникли две критические проблемы:
1. **Динамика обучения (Сходимость):** За 2000 шагов на батче 64 (обработано больше сэмплов, чем за 9000 шагов на батче 8) метрики практически не улучшились. Это произошло из-за того, что старые гиперпараметры (LR и EMA Decay) были настроены под маленькие батчи. Большой батч дает более точный градиент, но шагов делается меньше, поэтому старый LR оказался слишком консервативным.
2. **Скорость обучения (XLA Recompilation Loop):** Скорость упала до ~5 сэмплов в секунду, а время одного шага составило ~255 секунд. Анализ `metrics_report` показал постоянный рост метрики `UncachedCompile`. Причина: `CosineAnnealingWarmRestarts` и логика warmup обновляли `param_group["lr"]` (Python `float`) на каждом шаге. PyTorch XLA вшивает скалярные значения `lr` в граф как константы. Изменение этого числа на тысячные доли приводило к изменению хеша графа и принудительной JIT-компиляции (длительностью ~4 минуты) на каждом шаге.

## Решение (Decision)

### 1. Масштабирование Learning Rate (Square Root Rule)
Применено стандартное правило масштабирования $\sqrt{k}$, где $k=8$ (во столько раз увеличился батч: $64 / 8$). Множитель $\approx 2.8$.
- `dus_learning_rate` увеличен с `2e-5` до `5.6e-5`.
- `new_layers_lr` увеличен с `1e-4` до `2.8e-4`.

### 2. Корректировка EMA Decay
Значение `ema.decay` снижено с `0.998` до `0.99`.
- При старом батче (8) за 64 сэмпла происходило 8 шагов: $0.998^8 \approx 0.984$.
- При новом батче (64) за 64 сэмпла происходит 1 шаг. Если оставить `0.998`, инерция (momentum) теневых весов стала бы в 6 раз сильнее. Значение `0.99` возвращает инерцию к адекватному уровню (1% обновления на шаг в 64 сэмпла).

### 3. Ступенчатое обновление LR (Step-wise LR)
Для устранения XLA Recompilation Loop логика обновления `lr` в оптимайзере изменена:
- Значение `lr` обновляется строго раз в 50 шагов (`current_optim_step % 50 == 1`).
- Это гарантирует, что 49 шагов подряд XLA использует закэшированный бинарный граф (время выполнения миллисекунды). 
- Для Cyclic-расписания в `scheduler.step(current_optim_step)` передается абсолютный номер шага, чтобы внутренний таймер косинуса работал корректно, даже если `param_group["lr"]` обновляется не постоянно.

## Последствия (Consequences)
- **Позитивные:** 
  - Пропускная способность TPU восстановлена: ликвидированы холостые потери по 4 минуты на компиляцию графа.
  - Адаптация под Batch 64 ускорит выход из локальных минимумов за счет увеличенного шага градиента и сбалансированной EMA.
- **Негативные:** 
  - LR меняется "ступеньками" (каждые 50 шагов), что теоретически менее гладко, чем непрерывный косинус. Однако при батче 64 дисперсия градиентов достаточно низкая, чтобы это не повлияло на финальное качество.
